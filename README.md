# PixivDownloader 社区插件仓库

[English](README_en.md)

这里接收 PixivDownloader 插件投稿。将源码推送到公开 GitHub 仓库，等待候选 CI 通过，再在自己的源码工程中运行向导即可，无需克隆本仓库或手写投稿文件。

审核通过后，维护者在原申请 PR 中生成发布数据，合并后自动更新社区 Release。源码仓库的候选 Release 和审核中的社区 Draft 都不代表已获社区准入。

## 投稿与版本管理

### 1. 推送源码，等待 CI

- 使用 [Plugin SDK](https://github.com/Sywyar/PixivDownloader-Plugin-SDK) 开发插件，提交自己的许可证，并保留 SDK 工程标识和候选工作流。
- 将源码推送到公开仓库的默认分支，等待 **Plugin candidate** 的全部任务通过。CI 会测试、核对离线复现结果，并为每个插件复用一个 Draft Release，覆盖旧候选产物。
- 保持本地工作树干净，使用与 CI 相同的提交启动向导。无需手动下载 CI 附件或创建 Release；旧 SDK 工程须先升级配套工具并补齐候选工作流。

社区会从提交的源码重新构建并核对包字节。请固定构建工具、依赖和打包时间等输入，避免本地与社区环境差异导致包不一致。

### 2. 准备投稿环境

安装 Git、GitHub CLI、Node.js 24+ 和 JDK 17，确保终端可以运行 `java`、`javac`、`jar`。使用 Windows PowerShell 5.1 或 PowerShell 7，首次使用 GitHub CLI 时执行：

```powershell
gh auth login
gh auth setup-git
```

Git 还需配置提交用的 `user.name` 和 `user.email`。

需要代理时，Windows 可沿用系统代理；也可为终端设置 `HTTPS_PROXY`，用 `NO_PROXY` 指定直连目标。插件包与源码下载支持 HTTP / HTTPS 代理。下载失败时，向导会显示错误码和失败阶段，便于区分网络问题与文件摘要不符。

### 3. 运行投稿向导

进入自己的 SDK 工程目录，把示例路径替换为实际路径：

```powershell
Set-Location -LiteralPath 'D:\Plugins\example'
irm 'https://raw.githubusercontent.com/Sywyar/PixivDownloader-community-plugins/master/tools/submit.ps1' | iex
```

按提示完成以下内容：

1. 选择版本投稿。单一工程和构建方式会自动识别；有多个选项时再选择。向导会获取此提交的 CI 候选并核对包字节。
2. 核对插件版本、能力声明和许可证，选择自己的 GitHub 发布者身份，填写插件介绍等展示信息。
3. 选择已有签名密钥或生成新密钥。生成时选择一个已有的父目录，工具会在其中建立专用子目录；可以设置密码保护私钥。
4. 先确认提交摘要，再核对完整预览和元数据变化。确认执行后，向导会将已核对的候选保存为绑定源码提交的 Pre-release，生成所需的 fork、提交和投稿 PR。后续 CI 继续复用草稿，不覆盖已投稿的包。

私钥须保存在 Git 仓库和临时目录之外，并自行备份。加密私钥在需要签名时询问密码；向导不保存密码。若需修改版本、能力声明或源码中的许可证，请提交并推送修改，等待新 CI 通过后继续。

方向键移动，Enter 选择，空格勾选标签，Ctrl+B 返回上一步，Ctrl+S 保存退出，Esc 或 Ctrl+C 取消。可选字段可以清空。所有远端写入均提前展示并确认，确认项默认取消。

填写记录和已核验的包缓存在用户文件夹中，按源码仓库、插件工程和插件 ID 隔离，并区分 GitHub 账号；Windows 默认位于 `%LOCALAPPDATA%\PixivDownloader\community-submission\projects\`。再次运行时，向导用上次选择的语言询问是否继续。选择“是”会接着未完成的位置操作；选择“否”按普通流程开始，已有资料和密钥路径仍可预填。已签名且只差提交的内容会重新验签，无需再次输入密码；账号、源码或社区主线改变时会提示重新开始。

耗时操作会临时显示正在执行的子步骤，完成后收起。临时 GitHub 读取失败会自动重试；仍失败时可选择重试或保存退出。写入响应丢失时，向导先核对远端结果，再继续操作。

Actions 附件过期后仍可使用 Draft Release。草稿只保留最新候选；归档缺失时，向导可在确认后重跑默认分支当前提交的 CI。已经确认投稿的固定候选继续保留。

许可证步骤可以使用现有文件，也可以从内置模板创建新文件。工具保留原有文件，识别到完整模板时会预选 SPDX 标识；组合许可仍需确认表达式。创建或修改许可证后，请提交、推送并等待新 CI。

### 4. 等待审核

在 PR 中查看检查结果和审核意见。社区会检查投稿、重建插件包、扫描声明并进行人工审核。仅等待审核不需要再次构建；源码、包或构建输入改变后需要重建并重新审核。

更新插件时，修改版本、推送并等待 CI，再运行同一入口。向导会读取上次的许可证和市场资料，保留已有语言与图片，并提前检查重复 ID 和版本。换钥、下架、恢复、撤销和转移所有权使用独立管理选项。

- 取消审核：选择“取消尚未合并的投稿或管理请求”，确认后关闭自己的 PR，再单独选择是否删除该请求分支。每次删除都重新确认；分支已有新提交、受到保护或仍被其它开放 PR 使用时会保留。普通作者清理自己 fork 中的分支，社区所有者清理本仓库中的投稿分支。整个 fork、默认分支、Release、密钥和填写记录均保留。已合并但尚未执行的请求请联系维护者暂停执行。
- 下架与恢复：YANK 阻止新安装；修复问题后可用 UNYANK 恢复自己发起的下架。社区独立限制继续有效。
- 撤销版本：REVOKE 用于阻止安装与启动，不能恢复，须输入所选的 `插件ID@版本` 确认。客户端按其支持的撤销协议执行限制。
- 换钥：选择发布者和新密钥；旧密钥遗失时进入人工恢复审核。
- 转移：接收方用自己的密钥创建请求，原维护者随后在向导中选择该请求并批准。双方无需交换私钥；无法取得原维护者批准时须提供恢复证据并接受单独审核。

当前个人管理者用活动密钥签署的 YANK、UNYANK、REVOKE 请求，由受保护流程核验后在原 PR 追加结果，检查通过后自动合并并更新 Release，无需重新构建或等待人工批准。原生人工拒绝仍会阻断；缺少密钥、组织代表权或涉及社区独立限制的恢复请求须人工审核。换钥和所有权转移继续人工审核。

向导复用已有 fork，每次请求从社区当前主线创建分支，无需同步 fork 的默认分支。临时 Git 副本退出时自动清理；向导退出后不追踪请求合并，也不清理远端分支。

正式 Release 的名称包含原发布者，后续状态和当前维护者会更新到说明中；原包、历史签名和原作者记录保持不变。没有适用对象时，向导说明原因并返回操作菜单。
